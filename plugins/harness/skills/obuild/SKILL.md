# obuild — 빌드·기동 전담 (단일 에이전트 독점)

> **프로젝트별 빌드/기동/종료 명령**: `oinfra_{project}` 의 "빌드 방법" · "배포 설정" 섹션 참조.
> 이 스킬은 100% 범용이다. 프로젝트명·경로·포트·계정을 본문에 기재하지 않는다.

## 왜 필요한가 (실측 근거)

```yaml
문제_1_빌드_경합:
  현상: 여러 에이전트가 동시에 빌드를 실행하면 산출물 파일 잠금이 충돌한다.
  실측: 한 에이전트의 컴파일 오류 1건이 다른 에이전트의 검증을 전면 차단했다.
  실측: 실행 중 프로세스가 산출물을 잡고 있어 빌드가 "파일이 잠겨 있습니다" 로 실패했다.
  해법: 빌드·기동은 obuild 에이전트 1개만 수행한다. 나머지는 요청만 보낸다.

문제_2_기동_확인_부재 (본 스킬 신설의 최대 이유):
  현상: 기동 명령은 프로세스 생성을 "요청"할 뿐, 실제로 떴는지 알려주지 않는다.
  실측: 잘못된 구동 명령 · 런타임 오류 · 런타임 설치 안내 모달 로 기동이 실패했다.
  실측: 기동 확인 절차가 없어 "기동 실패" 를 "간헐 종료" 로 오인해 집계했다.
  해법: 기동 후 프로세스 실존 확인(⑤) + 기동 로그 확인(⑥) 을 반드시 수행한다.
  원칙: ⑤⑥ 이 없으면 이 스킬을 실행한 의미가 없다.
```

## 핵심 원칙 (절대 규칙)

```yaml
1_독점: 빌드·기동 명령의 실행 권한은 obuild 담당 에이전트 1개에만 있다.
2_분업: 다른 odev 에이전트는 코드 수정만 수행한다. 빌드 명령 직접 실행을 금지한다.
3_요청_회신: 빌드 요청은 SendMessage 로 받고, 결과를 SendMessage 로 회신한다.
4_직렬화: 동시에 도착한 복수 요청은 큐로 직렬 처리한다. 병렬 빌드를 금지한다.
5_합류: 대기 중 추가 요청이 도착하면 1회 빌드로 합류시키고 요청자 전원에게 회신한다.
```

## 필수 절차 ① ~ ⑥ (순서 엄수)

### ① 사전 정리 — 실행 중 프로세스 종료

```yaml
목적: 실행 중 프로세스가 산출물을 잡고 있으면 빌드가 파일 잠금으로 실패한다.
명령: oinfra_{project} 의 shutdown/종료 명령 참조
확인: 종료 명령 후 프로세스 목록을 재조회하여 잔존 0건을 확인한다.
잔존_시: 강제 종료 후 재확인. 2회 실패 시 빌드를 착수하지 않고 요청자에게 보고한다.
주의: 종료 대상은 이번 빌드 대상 산출물의 프로세스로 한정한다. 무관 프로세스 종료 금지.
```

### ② 빌드 — 증분 금지

```yaml
명령: oinfra_{project} "빌드 방법" 섹션 참조
필수_옵션: 증분 빌드 비활성화(예: --no-incremental 상당 옵션)
  이유: 증분 빌드는 이전 빌드에서 이미 처리된 파일의 경고를 재출력하지 않아
        경고 수가 부정확해진다. baseline 대조가 무의미해진다.
성공_감지: 빌드 도구의 성공 문자열
실패_감지: 빌드 도구의 실패 문자열
로그_보존: 빌드 출력 전문을 $HOME/.claude/session-env/${UUID}/logs/ 에 저장한다.
```

### ③ 오류 판정 — 담당 에이전트 특정

```yaml
목적: 오류를 낸 파일의 담당 에이전트에게 직접 통보해야 수정이 빨라진다.
절차:
  1. 빌드 출력에서 오류 라인을 파싱한다 (파일 경로 · 라인 · 오류 코드 · 메시지).
  2. 파일 경로를 담당 에이전트에 매핑한다.
  3. 매핑 결과를 회신에 포함한다.

매핑_소스 (우선순위):
  1순위: $HOME/.claude/session-env/${UUID}/file_assignment.json
         - odev_parallel 이 파일 할당 시 생성하는 매핑 (에이전트명 → 담당 파일 목록)
         - 조회: 오류 파일 경로가 어느 에이전트의 담당 목록에 속하는지 검색
         - ⚠️ 단독 사용 금지 — 반드시 아래 "활성 인스턴스 대조" 를 병행한다.
  2순위: 파일이 없거나 매칭 실패 시 — Intent Lock(.claude/locks/*.json) 의 파일 소유자 조회
  3순위: 그래도 미상이면 담당 "미상" 으로 표기하고 요청자와 리더 양쪽에 통보한다.

★ 활성_인스턴스_대조 (필수 — L-666, 2026-08-23 사이클25 실사고):
  배경: |
    odev-3 이 빌드 오류를 `odev-4` 에 통보했으나, 그건 ★이전 사이클 잔류 인스턴스★(1h 전,
    이미 shutdown)였다. 실제 담당은 `odev-4-2`(9m 전)였다.
    odev-3 은 file_assignment.json 만 보고 담당자를 특정했고, 통보 대상이 살아 있는
    인스턴스인지 확인하지 않았다.
    그쪽의 "내 담당 아니다" 반박도 그 인스턴스 기준으로는 사실이라
    ★두 진술이 모두 참★ 인 상태가 됐다.
  ⇒ 계획서는 "누가 맡기로 했나" 이지 "지금 누가 살아있나" 가 아니다.

  절차 (통보 ★전★ 수행):
    1. ListAgents 를 호출해 현재 살아 있는 에이전트 목록을 확보한다.
    2. file_assignment.json 이 지목한 이름이 그 목록에 ★존재하는지★ 확인한다.
    3. 같은 접두어의 재spawn 인스턴스(예: odev-4 vs odev-4-2)가 보이면

         - ListAgents 의 기동 시각이 현재 파이프라인 진입 이후인가
```

### ④ 기동

```yaml
명령: oinfra_{project} "배포 설정" 섹션의 기동 명령 참조
주의: 기동 명령은 프로세스 생성을 요청할 뿐 성공을 보장하지 않는다.
      반드시 ⑤ 로 이어진다. ④ 만 하고 "기동 완료" 를 선언하는 행위를 금지한다.
```

### ⑤ ★ 기동 확인 — 프로세스 실존 확인 (핵심)

```yaml
목적: 기동 명령 반환은 성공 신호가 아니다. 프로세스가 실제로 살아 있는지 물리 확인한다.
방법:
  Windows 대상: tasklist 로 실행파일명 필터 조회
  Linux/원격 대상: ps / pgrep / systemctl status 로 조회
확인_시점: 기동 직후 즉시 1회, 그리고 짧은 간격 후 1회 (총 2회).
  이유: 즉시 확인만 하면 "떴다가 곧바로 죽는" 경우를 놓친다.
       2회차에서 사라졌으면 기동 실패로 판정한다.
판정:
  프로세스 있음 (2회 모두) → ⑥ 으로 진행
  프로세스 없음 → 기동 실패 확정. 아래 "기동 실패 진단 체크리스트" 를 실행한다.
금지: 프로세스 확인 없이 "기동 성공" 을 보고하는 행위. 이 스킬의 존재 이유를 무효화한다.
```

### ⑥ 로그 확인 — 기동 로그가 실제로 남았는가

```yaml
목적: 프로세스가 떠 있어도 초기화에 실패했을 수 있다. 로그가 유일한 증거다.
방법: oinfra_{project} 의 로그 경로 참조 → 이번 기동 시각 이후의 로그 라인 존재 확인
판정:
  로그 있음 + 오류 없음 → 기동 성공 확정
  로그 없음            → 프로세스는 떴으나 초기화 실패. 실패로 판정한다.
  로그 있음 + 치명 오류 → 실패로 판정하고 오류 요약을 회신에 포함한다.
시각_대조: 기존 로그 잔존물을 성공으로 오인하지 않도록, 기동 시각 이후 라인만 인정한다.
```

## 기동 실패 시 진단 체크리스트

⑤ 또는 ⑥ 이 실패로 판정되면 아래를 순서대로 점검하고 결과를 회신에 포함한다.

```yaml
1_산출물_존재: 빌드 산출물(실행파일 · 라이브러리 · 런타임 설정 파일)이 출력 경로에 존재하는가.
  결손 시 → 빌드는 성공했으나 배포/복사 단계가 누락된 것이다.

2_런타임_모달_창: 런타임 설치 안내 등 모달 창이 떠서 기동이 멈춰 있는가.
  확인 → 화면 캡처로 시각 확인. 모달이면 기동 명령이 아니라 런타임 부재가 원인이다.

3_시스템_이벤트_로그: OS 이벤트 로그(애플리케이션 로그)에 크래시 기록이 있는가.
  Windows: 이벤트 뷰어 Application 로그 / Linux: journalctl · dmesg

4_런타임_버전_불일치: 실행에 필요한 런타임 버전과 설치된 버전이 일치하는가.
  호스트 정책 로딩 실패 · 런타임 버전 불일치 오류 문자열을 확인한다.

5_기동_명령_자체: 작업 디렉토리 · 인자 · 경로 인용이 올바른가.
  경로 변환(WSL↔Windows 등)이 필요한 대상인지 확인한다.

6_권한: 실행 권한 · 포트 점유 · 파일 접근 권한 문제인가.

보고: 위 6항목 중 원인으로 확정된 항목과 근거를 회신에 명시한다.
금지: 원인 미확인 상태에서 "간헐적 현상" 으로 분류하는 행위. 미확인은 미확인으로 보고한다.
```

## 증거 파일

```yaml
빌드_성공: touch "$HOME/.claude/session-env/${UUID}/evidence/build_ok"
기동_성공: touch "$HOME/.claude/session-env/${UUID}/evidence/run_ok"
  ⚠️ run_ok 는 ⑤ 프로세스 실존 확인 + ⑥ 로그 확인 을 모두 통과한 후에만 생성한다.
     기동 명령 반환만으로 run_ok 를 생성하는 행위를 금지한다.
검증_규칙: evidence mtime > pipeline_start_time (이전 세션 잔존 증거는 무효)
확인: ls "$HOME/.claude/session-env/${UUID}/evidence/"
```

## 요청 큐 처리

```yaml
수신: SendMessage 로 "빌드 요청" 을 받는다. 요청에는 요청자 에이전트명이 포함된다.
직렬: 빌드 진행 중 도착한 요청은 대기시킨다. 동시 빌드를 절대 실행하지 않는다.
합류: 대기 요청이 여럿이면 1회 빌드로 합류 처리하고 요청자 전원에게 동일 결과를 회신한다.
거절: 진행 중인 빌드가 없고 코드 변경도 없으면 빌드를 스킵하고 그 사실을 회신한다.
```

## 결과 회신 형식 (고정)

```
[빌드 결과] 요청자 {에이전트명}
빌드 : 오류 {N} 경고 {N} (baseline {N})
오류 : {파일:라인} — 담당 {에이전트}
기동 : {프로세스 조회 결과 — 있음/없음}
로그 : {기동 로그 확인 결과}
```

```yaml
실패_시_추가: 진단 체크리스트 결과(확정 원인 + 근거)를 회신 하단에 붙인다.
전송: SendMessage(to:"{요청자}", message:"{위 형식}", summary:"obuild 결과 회신")
리더_통보: 오류 담당이 요청자와 다르면 담당 에이전트와 리더에게도 각각 통보한다.
```

## 파이프라인 내 호출 시

```yaml
성공: SendMessage(to:"{리더명}", message:"obuild 완료\n{대상 목록}\n증거: evidence/build_ok, evidence/run_ok", summary:"obuild 완료")
실패: SendMessage(to:"{리더명}", message:"obuild 실패\n원인:{1줄}\n권고: odev 역라우팅", summary:"obuild 실패")
```

## 금지 사항

```yaml
- obuild 이외 에이전트의 빌드/기동 명령 직접 실행
- ⑤ 프로세스 확인 없이 기동 성공 보고
- ⑥ 로그 확인 없이 run_ok 증거 생성
- 증분 빌드 결과로 경고 수 판정
- obuild 가 타 에이전트 담당 파일을 임의 수정
- 원인 미확인 실패를 "간헐 현상" 으로 분류
```
