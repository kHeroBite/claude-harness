# oimprove — 코드베이스 누적 부채 정리 스킬

> 출처: improve-codebase / improve-codebase-architecture (mattpocock/skills, MIT 라이선스 영감)
> 본 스킬은 한국어 환경에 맞게 재구성되었으며, 코드 자체 수정은 ok 파이프라인에 위임한다.

---

## 핵심 원칙

```yaml
주기성: 수일~수주에 1회 (예방적 청소 — 너무 자주 호출하면 노이즈)
호출_방식: 사용자 명시 호출 전용 (자동 트리거 절대 금지)
역할_분담: 분석 + 후보 추출이 본 스킬, 실제 수정은 ok 파이프라인 위임
철학: "AI에게 쓰레기 코드를 주면 쓰레기를 만든다 — 코드베이스를 깨끗하게 유지하는 것이 AI 협업의 기반"
```

본 스킬은 **분석 전담**이다. 직접 코드 수정 절대 금지. 분석 결과를 사용자가 검토한 뒤 `/o3` 또는 `/o4` 파이프라인으로 위임한다.

---

## 다른 스킬과의 차별화

| 스킬 | 시점 | 대상 | 자동성 |
|---|---|---|---|
| odev_simplify | 방금 작성 직후 | 새로 작성한 코드 | 자동 (medium/full odev 후) |
| oinsights | 사용자 명시 | 세션 마찰 (메타) | 수동 |
| oretro | 주기적 | 커밋 트렌드 | 수동 |
| **oimprove** | **수일~수주 1회** | **코드베이스 자체** | **수동** |

- **oinsights**: 세션 메타분석 (어떤 작업이 마찰을 일으켰는가) — 코드를 읽지 않음
- **odev_simplify**: 직후 정리 (방금 만든 코드 단순화) — 누적분에는 무력
- **oretro**: 커밋 트렌드 (어떤 영역이 자주 수정되는가) — 코드 품질 직접 평가 안 함
- **oimprove**: 코드 자체 평가 (얕은 모듈/중복/순환의존성/네이밍 등) — 누적 부채 청소 전담

---

## 점검 항목 (체크리스트)

| # | 항목 | 판정 기준 |
|---|------|---------|
| 1 | **얕은 모듈** | 함수/클래스 1~2개만 있는 파일 또는 디렉토리 |
| 2 | **중복 코드** | 동일/유사 로직 3곳 이상 반복 |
| 3 | **순환 의존성** | 모듈 A → B → A 등의 import 순환 |
| 4 | **네이밍 일관성** | snake_case vs camelCase 혼용, 약어 불일치 (예: `usr_id` vs `user_id`) |
| 5 | **도메인 언어 정합성** | PROJECT.md 용어집과 변수/함수명 비교 |
| 6 | **죽은 코드** | 참조 0인 함수/변수/파일 |
| 7 | **거대 파일/함수** | 500줄+ 파일, 100줄+ 함수 |
| 8 | **ADR 일관성** | docs/adr/ 결정 사항이 코드에 실제로 반영되어 있는가 |

각 항목은 정량 지표(점수 N/8)로 보고된다. 0건이어도 정상 — 이미 깨끗하다는 신호다.

### deletion test 원칙 (mattpocock 핵심 영감)

> "이 모듈을 삭제하면 무엇이 깨지는가? 깨지는 것이 적다면 그 모듈은 얕다."

- **깊은 모듈**: 인터페이스가 작고 구현이 큰 모듈 — 삭제 시 많은 호출부가 깨진다 (가치 큼)
- **얕은 모듈**: 인터페이스 == 구현인 모듈 — 호출부가 직접 구현해도 무방 (가치 작음)

얕은 모듈은 인라인화 후보. 단, 도메인 추상화 가치가 있다면 유지한다 (사용자 판단).

## 실행 절차

### Step 1. 범위 결정
사용자에게 범위 명시 요청 (디렉토리 또는 모듈). 범위가 모호하면 oplan 팀에이전트가 5축 결손 판정 후 명확화 인터뷰를 수행한다.

### Step 2. 도메인 언어 + 결정 사항 파악
- `PROJECT.md`의 용어집(있다면) 읽기
- `docs/adr/` 디렉토리의 ADR 파일 읽기 (Architecture Decision Records)
- 도메인 언어 매핑 표 작성 (변수명/함수명이 도메인 용어와 일치하는가)

### Step 3. 8개 항목 스캔
- `mcp__oio__find` / Glob: 파일 크기, 디렉토리 구조
- `mcp__oio__bash_exec` (grep/wc): 함수/클래스 개수, 라인 수
- Serena (C# 프로젝트인 경우): `find_referencing_symbols`로 죽은 코드 탐지
- 모든 도구 사용은 읽기 전용 (수정 금지)

### Step 4. 후보 추출
영향도(큼/중/작) × 리스크(낮/중/높) 매트릭스로 우선순위 결정.

### Step 5. 사용자 보고
8개 항목별 점수 + 권장 우선순위 1~N순위를 출력 (아래 출력 형식 참조).

### Step 6. ok 파이프라인 위임
사용자 승인 시 1순위 항목을 `/o3` 또는 `/o4`로 위임. 위임 시 oplan에 본 분석 결과를 컨텍스트로 전달.

**금지**: 본 스킬은 직접 코드 수정 절대 X (분석 단계 전용)

```text
📊 [oimprove] 코드베이스 부채 분석 — {범위}

## 점검 항목별 후보

### 1. 얕은 모듈 (점수: N/8)
- {파일 경로}: {이슈 요약 + deletion test 결과}
- {파일 경로}: ...

### 2. 중복 코드 (점수: N/8)
- {파일 1}:{라인} ↔ {파일 2}:{라인}: {동일 로직 요약}

### 3. 순환 의존성 (점수: N/8)
- {모듈 A} → {모듈 B} → {모듈 A}

### 4. 네이밍 일관성 (점수: N/8)
- snake_case vs camelCase 혼용: {예시 N건}
- 약어 불일치: usr_id vs user_id ({위치})

### 5. 도메인 언어 정합성 (점수: N/8)
- PROJECT.md 용어 "{용어}" 미반영: {코드 위치}

### 6. 죽은 코드 (점수: N/8)
- {함수/변수}: 참조 0건 ({위치})

### 7. 거대 파일/함수 (점수: N/8)
- {파일}: NNN줄 (임계 500줄 초과)
- {함수}: NN줄 (임계 100줄 초과)

### 8. ADR 일관성 (점수: N/8)
- ADR-NNN: {결정 사항} → 코드 미반영 위치: {파일}

## 권장 우선순위

1순위: {항목} — 영향: {큼/중/작}, 리스크: {낮/중/높}, 추정 작업 tier: {o2/o3/o4}
2순위: ...
3순위: ...

## 다음 단계 권장

- 1순위 진행: /o4 1순위 항목 리팩토링
- 2~3순위 보류: 사용자 검토 후 결정
- 0건이어도 정상 — 이미 깨끗하다는 신호
```

## 사용 시점 가이드

```yaml
권장:
  - 수일~수주에 1회 (분기/스프린트 회고 시)
  - 큰 기능 추가 직전 (정리 후 진행 — 새 기능이 부채 위에 쌓이는 것 방지)
  - 신입 합류 전 (코드 가독성 확보)
  - 외부 영상 권고: "every few days" 또는 회고 사이클

비권장:
  - 매일/매시간 호출 (노이즈만 양산)
  - 기능 구현 도중 호출 (집중력 분산 — odev_simplify가 담당)
  - 새로 시작한 프로젝트 (부채가 누적되지 않은 시점)
```

## 주의사항

- **자동 호출 X**: 본 스킬은 수동 전용. UserPromptSubmit hook의 권장 메시지는 "권장"일 뿐 자동 spawn 없음.
- **임의 수정 금지**: 분석 결과를 사용자가 검토하지 않고 LLM이 임의 수정하는 행위 금지. 항상 사용자 승인 후 ok 파이프라인 위임.
- **0건은 정상**: 점검 결과 0건이어도 실패 아님. 이미 깨끗하다는 긍정적 신호.
- **도메인 가치 보존**: 얕은 모듈이라도 도메인 추상화 가치가 있다면 유지. 인라인화는 사용자 판단.
- **ok 파이프라인 위임**: 분석 → 위임 시 oplan이 본 결과를 ground_truth로 활용하므로, 부정확한 분석은 후속 사이클에 누적됨. 정확성 우선.
