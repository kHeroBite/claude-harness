# odebug — 체계적 디버깅

> 독립 유틸리티 스킬 — 모든 파이프라인 단계에서 호출 가능

## 호출 분기

```yaml
사용자_직접_호출 (/odebug 슬래시 명령):
  판단_기준: system-reminder에 `💬 [IDLE 직접처리]` 또는 `⚡ [슬래시 명령] oi 바이패스 — /odebug` 컨텍스트
  동작: 팀에이전트 spawn (메인 컨텍스트 보호)
  절차:
    1. entry_tier=OK 기록 (IDLE 유지 — state 전이 절대 금지)
       mcp__oio__session_state(uuid="${UUID}", key="entry_tier", value="OK")
    2. TeamCreate (무조건 — 새 세션이므로 항상 신규 팀 생성)
    3. Agent 팀에이전트 spawn:
       Agent(subagent_type="general-purpose", team_name="{팀명}", name="odebug-worker",
             mode="bypassPermissions",
             prompt="Skill('odebug') 호출. 내부_호출=true. 사용자 요구사항: {원문}. PIPELINE_UUID={UUID}")
    4. 완료 수신 → ofinish(경량 — TeamDelete + IDLE)
  state_원칙: IDLE 유지 (state=PLAN/DEV/TEST 설정 절대 금지)

내부_호출 (otest_run/ok_pipeline/otestui/odev에서 호출 시 또는 내부_호출=true 플래그):
  판단_기준: 호출 컨텍스트가 팀에이전트 (PIPELINE_UUID 보유) 또는 내부_호출=true 명시
  동작: 아래 Quick Debug / 경량 모드 / Standard Debug 4 Phase 직접 실행 (기존 동작 유지)
  비고: 파이프라인 내부 호출은 spawn 강제하지 않음 (이중 spawn 방지)
```

## Quick Debug 분기 (명백한 단순 오류)

```yaml
Quick_Debug_조건: (AND — 모두 충족 시)
  - 오류 원인이 명백 (오타, 상수 오류, off-by-one 등)
  - 단일 파일 수정으로 해결 가능
  - 사이드 이펙트 없음

Quick_Debug_절차:
  - Phase 1 스킵 (조사 불필요 — 원인 자명)
  - Phase 2: 패턴 매칭만 (30초)
  - Phase 3 스킵 (가설 불필요)
  - Phase 4: 즉시 수정
```

## 경량 모드 (간단 버그)

```yaml
경량_모드_조건:
  - 원인이 명백 (오타, 상수 오류, 단순 로직 실수)
  - Quick Debug보다는 복잡하나 Phase 2-3이 불필요한 수준

경량_모드_절차:
  Phase 1(조사) → Phase 4(수정) 직행 (Phase 2-3 생략)

판단_기준:
  원인이 30초 내 식별되면 경량 모드 적용
  30초 초과 시 Standard Debug(4 Phase) 전환
```

> Quick Debug / 경량 모드 조건을 충족하지 않으면 아래 Standard Debug(4 Phase)를 따릅니다.

## 철칙 (Standard Debug)

```
근본 원인 조사 없이 수정 금지
Phase 1 완료 전 수정 제안 불가
자기 작성/수정 코드는 더 회의적으로 봐야 한다 — 설계 의도가 아닌 코드의 실제 동작만 판단 근거로 삼아라
```

**경고 신호 (철칙 위반 감지):**
```yaml
자기코드_회의_위반_신호:
  - "이 부분은 내가 올바르게 구현했으니 다른 데서 찾아보자"
  - "이건 이렇게 동작해야 해" (검증 없이)
  - "이 접근법은 테스트했어" (증거 없이)
  대응: 코드의 실제 동작만 신뢰. 의도는 증거가 아님.
```

## Phase 1: 근본 원인 조사

**모든 수정 전 필수:**

1. **에러 메시지 주의 깊게 읽기**
   - 스택 트레이스 완전히 읽기
   - 줄 번호, 파일 경로, 에러 코드 기록
   - 건너뛰기 금지

2. **일관되게 재현**
   - 정확한 트리거 단계 확인
   - 재현 불가 → 더 많은 데이터 수집 (추측 금지)

3. **최근 변경사항 확인**
   - Git diff, 최근 커밋
   - 새 의존성, 설정 변경, 환경 차이

4. **다중 컴포넌트 증거 수집**
   - 각 컴포넌트 경계마다 진입/이탈 데이터 로그
   - 환경/설정 전파 검증
   - 한 번 실행하여 실패 컴포넌트 식별

   **Layer별 진단 템플릿** (수정 전 각 컴포넌트 경계에 진단 계측 추가):
   ```csharp
   // Layer 1: Controller 입력
   _logger.LogDebug("[Layer1-입력] userId={UserId}, req={@Req}", userId, request);
   // Layer 2: Service 경계
   _logger.LogDebug("[Layer2-서비스] 처리 시작, data={@Data}", data);
   // Layer 3: Repository/DB 경계
   _logger.LogDebug("[Layer3-DB] 쿼리 실행, params={@Params}", params);
   // Layer 4: 결과
   _logger.LogDebug("[Layer4-결과] result={@Result}", result);
   ```
   절차: (1) 관련 컴포넌트 경계 식별 (최대 4-5개 Layer) → (2) 각 Layer 진입/이탈 지점에 진단 로그 삽입 → (3) 한 번 실행 → 어느 Layer에서 끊어지는지 확인 → (4) 실패 Layer 집중 조사 → (5) 근본 원인 확인 후 진단 로그 제거 (임시 코드)

5. **데이터 플로우 추적**
   - 나쁜 값의 발생 위치 → 위로 추적
   - 증상이 아닌 소스에서 수정

6. **외부 지식 수집** — 에러 메시지 → 웹 검색으로 알려진 이슈 확인, 프레임워크 동작 → context7로 공식 문서 확인
7. **Codex 구분** — 위 외부 지식 수집(Phase 1 초기 정보수집)은 Codex 리뷰(3회 실패 후 코드분석)와 시점·목적 상이

## Phase 2: 패턴 분석

1. **작동하는 예시 찾기** — 코드베이스에서 유사한 작동 코드
2. **참조와 비교** — 모든 줄 읽기, 훑어보기 금지
3. **차이점 식별** — 아무리 작아도 모든 차이 나열
4. **의존성 이해** — 필요한 컴포넌트, 설정, 가정

## Phase 3: 가설 및 테스팅

### 교착 대응 (othink 흡수)

> 교착 상태(가설 2회+ 실패) 시 아래 5가지 모드 중 1개만 선택하라.

**모드 1: 재정의 (Reframe)** — 문제 정의 자체 재검토
- 현재 문제를 1문장으로 기술 → 반전("버그가 아니라 의도된 동작이라면?") → 범위 확대/축소 → 유사 패턴 탐색
- 출력: 재정의된 문제 1문장 + 근거 1문장

**모드 2: 대안 매트릭스 (Alternatives)** — 접근법 비교
- 대안 최대 4개 열거 → 실현가능성(1-5) × 가치(1-5) / 위험(1-5) = 점수
- 차이 ≥ 2.0 → 최고 점수 채택 / 차이 < 2.0 → 추가 분석
- 출력: 점수 테이블 + 선택 근거 1문장

**모드 3: 레버리지 (Leverage)** — 최소 변경 최대 효과 지점
- 관련 컴포넌트 5개 이내 + 의존성 흐름(A → B → C) → 최다 하류 영향 지점 식별
- 출력: "레버리지 포인트: [심볼/파일] — [기대 연쇄 효과]"

**모드 4: 되돌아가기 (Revision)** — 이전 가정 재검토
- 수행한 단계 나열 → 의심 단계 지목 → 가정 재검증(코드/로그/데이터)
- 출력: "재검토: Step N → 수정된 가정 + 영향받는 후속 판단"

**모드 5: 분기 탐색 (Branch)** — 두 경로 비교
- 분기점 명시 → 각 분기 3단계까지(깊이 제한) → 결과/위험 비교 → 선택 + 확신도
- 출력: "분기 A: [결과] vs 분기 B: [결과] → 선택: [A/B] (확신도)"

```yaml
규칙: 1개 모드만 선택 / 재귀 금지 / 출력 500자 이내 / 교착 없으면 호출 금지
```

0. **문제 재정의 체크** (2회+ 가설 실패 시 필수):
   - 현재 정의가 올바른가?
   - 반대 관점: 버그가 아니라 설계 의도라면?
   - 범위 전환: 이 파일이 아니라 호출자/피호출자 문제라면?
   - 교착 시: /othink 재정의 모드
   ```yaml
   구조화된_중간보고 (가설 2회+ 실패 시 자동 발동):
     조건: 문제 재정의 체크 발동 시 (= 가설 2회+ 실패)
     출력_형식: |
       ## 디버깅 중간보고
       ### 증거: [관찰/확인된 사실]
       ### 조사: [확인/배제한 사항]
       ### 배제된 가설: [실패한 가설 + 실패 이유]
       ### 잠정 근본 원인: [현재 최유력 가설, 증거 기반]
       ### 권고 수정: [구체적 파일:라인 + 코드, 있으면]
       ### 리스크 평가: [사이드이펙트, 신뢰도]
     후속: 사용자가 Phase 4 진입 / 추가 조사 / /othink 선택
     기본: 자동 출력 후 Phase 3 계속 (사용자 응답 대기 아님, 기록용)
   ```

1. **단일 가설 형성**: "Y 때문에 X가 근본 원인"
2. **최소한으로 테스트**: 한 번에 하나 변수만
3. **계속 전 검증**: 통함 → Phase 4, 안 통함 → 새 가설
4. **반증 의무**: 각 가설에 대해 "이것이 참이면 무엇이 증명되나?" + "이것이 거짓이면 무엇이 증명되나?" 양방향 질문 필수. 양방향 검증 미충족 시 Phase 4 진입 금지.
5. **모를 때**: "이해 못함" 말하기, 아는 척 금지

## Phase 4: 구현

1. **실패 테스트 케이스 생성** (수정 전 필수)
2. **단일 수정 구현** — 한 번에 하나, "이왕 여기 왔으니" 금지
3. **수정 검증** — 테스트 통과, 다른 테스트 깨짐 없음

### 3회 실패 규칙

```yaml
수정_시도_카운트:
  < 3회: Phase 1로 복귀, 새 정보로 재분석
  == 3회 (순서 필수):
    1단계_Codex_리뷰: Codex MCP에 코드 리뷰 요청 (아래 Codex 리뷰 섹션 참조)
      → Codex 가이드로 해결: Phase 4 재진입 (수정 적용)
      → Codex 가이드 불충분: 2단계로
    2단계_othink: /othink 레버리지 모드 (최소 변경 최대 효과 지점 탐색)
      → 레버리지 포인트 발견: 해당 지점에서 Phase 1 재시작
      → 미발견: /oplan 복귀 (전체 재설계)
  > 3회: 절대 금지

아키텍처_문제_신호:
  - 각 수정이 다른 곳에 새 문제 드러냄
  - "대규모 리팩토링" 필요
  - 각 수정이 새 증상 생성
```

### Codex 코드 리뷰 (반복 실패 시 자동 발동)

> 공식 OpenAI Codex MCP(`codex`, `codex-reply`)를 활용한 외부 코드 리뷰.
> 동일 문제가 반복 실패 시, othink 전에 먼저 Codex에게 가이드를 요청한다.

```yaml
발동_조건 (OR — 하나라도 해당 시 자동 발동):
  A. odebug_내_3회_실패: Phase 4 수정 시도 3회 실패 (기존 3회 실패 규칙)
```

## 6단계 진단 절차 (diagnose 기법, 절대 규칙)

> 출처: diagnose (mattpocock/skills, MIT) — 의학적 감별 진단(differential diagnosis) 절차에서 차용. 모든 디버깅 작업은 이 6단계를 순차 수행하라. "수정만 하고 회귀 테스트 누락" 패턴 절대 금지.
>
> **기존 4 Phase와의 관계 (AC-S03)**: 본 6단계 절차는 기존 4 Phase(Root Cause / Pattern / Hypothesis / Implementation)의 **보완**이다. 충돌 발생 시 **기존 4 Phase 우선** 적용 — 6단계는 4 Phase 안에서 누락되기 쉬운 "재현/최소화/회귀 테스트"를 강제하는 체크리스트로 활용한다. 4 Phase가 흐름 가이드라면, 6단계는 종료 전 검증 게이트.

### Step 1. 재현 (Reproduce)
- 최소 명령/입력으로 버그 재현 확인
- 비결정적이면: 5회 시도하여 발생률 측정
- 재현 안 됨 → 환경 차이 의심 (OS/버전/시간/캐시)
- 출력: "재현 명령: {커맨드} | 발생률: {N/5} | 환경: {WSL2/NTFS/Python 3.x}"

### Step 2. 최소화 (Minimize)
- 무관한 코드/입력/설정 제거하여 트리거 코드 좁히기
- 큰 입력 → 절반씩 줄여가며 재현 유지되는 최소 입력 발견
- 큰 함수 → 부분만 남기고 호출 → 재현 여부 확인
- 출력: "최소 재현 코드: {N줄} (원본 {M줄}에서 축소)"

### Step 3. 가설 (Hypothesize)
- 근본 원인 후보 2~3개 나열 (1개만 잡으면 확증편향 위험 — 5대 인지편향 §1 참조)
- 각 가설은 검증 가능해야 함 ("느리다" X → "DB 쿼리 N+1 문제" O)
- 출력:
  ```
  가설 1: {원인 + 검증 방법}
  가설 2: ...
  가설 3: ...
  ```

### Step 4. 측정 (Instrument)
- 로그/print/디버거/프로파일러로 가설 검증
- 가설 1 확인 → 측정 데이터로 PASS/FAIL 판정
- 모든 가설 FAIL → Step 3으로 돌아가 새 가설
- 측정 도구: print/logging/breakpoint/strace/perf/Wireshark 등 적절히 선택
- 출력: "가설 1 측정 결과: {데이터 + 판정}"

### Step 5. 수정 (Fix)
- 검증된 원인만 수정 — "측정 안 했지만 의심되는 것" 동시 수정 금지 (회귀 위험)
- 최소 변경: 원인 코드만 수정. 주변 정리는 별도 작업
- 출력: "수정 파일: {경로}, diff: {요약}"

### Step 6. 회귀 테스트 (Regression-test)
- 그 버그를 영구히 잡는 테스트 추가 (절대 필수)
- 테스트 위치: 프로젝트 테스트 디렉토리 (단위/통합 적절히)
- 테스트는 "버그 재현 입력 + 기대 동작" 형태
- 회귀 테스트 누락 = 같은 버그 재발 시 감지 불가 = 버그 미수정과 동급
- 출력: "회귀 테스트 추가: {파일:라인}, 검증: {pass}"

### 6단계 체크리스트 (디버깅 종료 전 확인)
- [ ] Step 1. 재현 성공 (발생률 명시)
- [ ] Step 2. 최소화 완료 (코드/입력 축소)
- [ ] Step 3. 가설 2~3개 명시
- [ ] Step 4. 측정 데이터로 가설 검증
- [ ] Step 5. 검증된 원인만 수정
- [ ] Step 6. 회귀 테스트 추가됨

체크리스트 미충족 시 디버깅 미완료로 간주.

### 6단계 절차 위반 시 패턴

| 위반 | 결과 |
|---|---|
| Step 1 생략 (재현 없이 수정) | 다른 버그 만들 가능성 |
| Step 2 생략 (최소화 없이) | 무관한 코드까지 의심 → 시간 낭비 |
| Step 3 생략 (단일 가설) | 확증편향, 진짜 원인 놓침 |
| Step 4 생략 (측정 없이 수정) | 추측 기반 수정, 재발 |
| Step 5 위반 (다중 동시 수정) | 무엇이 통했는지 격리 불가 |
| Step 6 생략 (회귀 테스트 X) | 같은 버그 재발 감지 불가 |

### 4 Phase × 6단계 매핑

| 4 Phase | 6단계 매핑 | 관계 |
|---|---|---|
| Phase 1 Root Cause | Step 1 재현 + Step 2 최소화 | Phase 1 안에서 재현/최소화 강제 |
| Phase 2 Pattern | (별도 — 6단계에 직접 매핑 없음) | 보완 영역 |
| Phase 3 Hypothesis | Step 3 가설 + Step 4 측정 | Phase 3의 양방향 검증과 동일 정신 |
| Phase 4 Implementation | Step 5 수정 + Step 6 회귀 테스트 | Phase 4 끝에 회귀 테스트 강제 |

원칙: 4 Phase는 흐름, 6단계는 종료 게이트. 두 절차의 출력이 충돌하면 4 Phase 흐름을 따르되, 6단계 체크리스트를 채우지 못하면 디버깅 미완료로 간주한다.

## Supporting Techniques

### defense-in-depth (근본 원인 수정 후 다층 방어)

```yaml
정의: 근본 원인 수정 후 동일 버그 재발을 막는 다층 방어 추가
적용_시점: Phase 4 근본 원인 수정 완료 후

다층_방어_레이어:
  Layer_1_입력_검증: Controller/API 경계에서 입력 값 범위/형식 검증
  Layer_2_비즈니스로직: Service 계층에서 불변식(invariant) 검증
  Layer_3_DB: 제약조건(NOT NULL, CHECK, FK) 활용
  Layer_4_모니터링: 예외 발생 시 경고 로그 + 알림

적용_기준:
  적용: 동일 버그 재발 가능 / CRITICAL 또는 데이터 손상 버그
  스킵: 1회성 오타, 명백한 단순 버그 (오버엔지니어링 방지)

주의: 방어 레이어 추가는 별도 커밋 (근본 원인 수정과 분리)
```

### condition-based-waiting (조건 기반 대기)

```yaml
정의: 임의 sleep(N) 대신 조건 충족 시까지 폴링
문제: Thread.Sleep(3000) 같은 임의 타임아웃 → 환경에 따라 불안정

C#_패턴:
  # ❌ 임의 대기 (금지)
  Thread.Sleep(3000);
  Assert.IsTrue(service.IsReady);

  # ✅ 조건 기반 대기
  var deadline = DateTime.UtcNow.AddSeconds(10);
  while (DateTime.UtcNow < deadline)
  {
      if (service.IsReady) break;
      Thread.Sleep(100);
  }
  Assert.IsTrue(service.IsReady, "서비스가 10초 내 준비되지 않음");

감지_Red_Flag: Thread.Sleep(N) with N > 500 테스트/디버그 코드
권장: condition-based-waiting 패턴으로 교체
```

## Red Flags — 중단하고 Phase 1 복귀

- "빠른 수정 하나만"
- "X 변경 시도하고 통하는지 보자"
- "여러 변경 추가 후 테스트"
- "아마도 X, 그거 고쳐보자"
- "완전히 이해 못하지만 통할지도"
- "한 번 더 수정 시도" (2회+ 실패 후)

```yaml
재시작_신호 (추가):
  - 조사 시작 후 진전 없이 시간만 경과 (30분+ 체크포인트)
  - "수정은 되는데 왜 되는지 모르겠음" → 이건 수정이 아니라 운
  - "디버거/로깅이 거짓말하는 것 같음" → 근본 전제가 틀림
  - 각 수정이 다른 곳에서 새 문제를 드러냄

재시작_절차:
  1. 현재까지 확실히 아는 것만 기록
  2. 배제한 가설 기록 (동일 가설 재시도 방지)
  3. 이전과 다른 새 가설 수립
  4. Phase 1부터 재시작 (이것은 실패가 아니라 전문성)
```
