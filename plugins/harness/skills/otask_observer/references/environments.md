# 환경, 활성화 설정, 핸드오프 문서 모드 (참조본)

설정 관련 질문, compact/재개 동작, 또는 파일시스템 접근이 없는 환경에서 이 파일을 로드한다.

## 권장 활성화 설정 (이 프로젝트 적용)

description 매칭만으로는 에이전트가 작업에 몰입한 상태에서 발동을 놓칠 수 있다. 원본은
CLAUDE.md류 설정 파일에 활성화 지시문을 병기하라고 권장하지만, 이 프로젝트는 이미 더
강한 물리적 강제 수단을 쓴다.

- **이 프로젝트의 실제 연동**: description 매칭 + hook 알림(`PostToolUse_observation_checkpoint.sh`)
  이중 구조. hook은 완료 이벤트(TodoWrite 등) 3건마다 stdout 알림을 출력해 "쓰는 행위"를
  유발한다 (SKILL.md "hook 연동 지점" 절 참조). 이는 원본이 제안하는 "CLAUDE.md 지시문
  병기"보다 강한 강제 수단이며, 이 프로젝트의 "재발방지 = 물리적 강제" 원칙에 부합한다.
- **CLAUDE.md 직접 수정 여부**: 본 담당(otask_observer 4파일)은 CLAUDE.md를 수정하지
  않는다 — Surgical Changes 원칙상 담당 범위 밖이며, hook 신설이 이미 원본이 요구하는
  "설정 계층 강제"의 역할을 대체한다.
- **안티패턴 (원본 이식)**: 활성화를 다른 스킬을 경유해 연쇄시키지 않는다 — otask_observer
  및 관련 스킬은 설정에서 독립적으로 로드되어야 한다. 연쇄 고리가 끊기면 관찰 활동 전체가
  조용히 무력화된다. 이 프로젝트에서는 이를 hook(설정 파일이 아닌 물리 스크립트)이
  담당하므로, hook 자체가 다른 hook에 의존해 조건부로만 실행되지 않도록 설계해야 한다
  (hook 구현은 별도 담당 소관, 여기서는 설계 원칙만 이식).

**설정 파일이 보호(governance-protected) 상태인 경우**: 이 프로젝트의 `write_guard.sh`
등은 특정 파일에 대한 쓰기를 의도적으로 차단할 수 있다. 차단이 발생하면 같은 편집을
맹목적으로 재시도하거나 우회하지 않는다 — 차단은 거버넌스 장치가 의도대로 작동한
것이며, 조용히 건너뛰는 것도 마찬가지로 나쁘다(사용자는 활성화가 됐다고 믿지만 실제로는
description 매칭만 살아있는 상태가 됨). team-lead에게 차단 사실을 보고한다.

## Compact/재개 동작

이 프로젝트에서 compact 이후에는 `ocontext` 스킬이 CLAUDE.md 등 변경된 설정을 재로드한다.
otask_observer의 관찰 로그(`session-env/${UUID}/logs/observations.md`)는 세션 UUID에
묶여 있으므로 compact로 세션이 이어지는 한 번호 체계(OBS-NNN)는 그대로 연속된다. 단,
완전히 새 세션(신규 UUID)으로 넘어가면 로그 파일도 새 UUID 하위에서 새로 시작된다 —
이는 원본의 "워크스페이스 고정 경로라 세션을 넘어 유지된다"는 전제와 다른 지점이며,
세션을 넘는 영구 보존이 필요한 통찰은 반드시 odone_lesson 승격을 거쳐야 하는 이유다.

## 핸드오프 문서 모드 (영속 저장소가 없는 환경)

방법론 자체는 환경 독립적이며 영속성만 환경마다 다르다. 파일시스템이 없는 대화형 환경
(예: 웹 채팅)에서는 세션 중 관찰을 모아 세션 종료 시 구조화된 핸드오프 문서로 제공하고,
사용자가 보관했다가 다음 세션에 붙여넣게 한다. **대화가 마무리되는 시점에 선제적으로
핸드오프를 제안한다** — 너무 이른 제안은 작은 방해지만, 누락되면 작업 전체가 유실된다.

```markdown
# 세션 핸드오프: [세션 주제]

**날짜:** [날짜]
**맥락:** [무엇을 작업했는지, 다음 세션이 알아야 할 것]

## 결정 사항
[번호 목록]

## 기록된 관찰
[표준 형식 전문]

## 교차 원칙 (현재)
[활성 또는 신규 추가]

## 액션 아이템
[재개에 필요한 맥락을 포함한 다음 단계]

## 작업 산출물
[초안/분석 전문]
```

이 프로젝트는 팀에이전트가 항상 `session-env/${UUID}/`라는 실제 파일시스템 저장소를
가지므로 핸드오프 문서 모드가 필요한 상황은 드물다. 다만 세션이 완전히 소멸하기 직전
(예: ofinish 직전, 아직 odone_lesson 승격이 끝나지 않은 경우) 관찰 로그의 OPEN 항목이
남아 있다면, 이 모드의 정신을 빌려 team-lead에게 요약을 남기는 것을 권장한다.

## 핸드오프 문서 분석 (수신 시)

1. 명시적으로 기술된 관찰을 먼저 필터링 없이 전부 기록한다.
2. 이어서 각 섹션을 체계적으로 읽으며 암묵적으로 함의된 스킬 공백이나 후보가 있는지
   묻는다 — 핸드오프 문서는 실시간으로 포착된 것 이상의 신호를 담는다.
3. 액션 아이템(각각 누락된 스킬을 암시할 수 있음), 열린 질문(모호함은 의사결정 프레임워크
   공백의 신호), 완료된 작업 서사(패턴이 메타 스킬을 드러낼 수 있음), 세션 메모에 특히
   주의한다.
4. 파생된 관찰은 원 세션이 아니라 "핸드오프 문서 분석에서 도출"로 출처를 표기한다.
