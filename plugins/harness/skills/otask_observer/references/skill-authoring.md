# 스킬 작성 규약 — 분류체계·라이선싱·기밀성·편집 규칙 (참조본)

신규 스킬을 만들거나 기존 스킬에 실질적 변경을 가하기 전에 이 파일을 로드한다.

## 분류체계 전문

**오픈소스 스킬**: 클라이언트에 무관하고 방법론 중심. 판별 기준 — 방법론이 여러
클라이언트/맥락에 걸쳐 통하는가, 독점 정보가 필요 없는가, 다른 실무자에게도 가치가
있는가, 개인 선호가 아니라 프로세스를 담고 있는가. 필수 요소 — 본문이 스스로 오픈소스임을
명시, 저작자 표시 블록, 라이선스 명시, 방법론 피드백을 원저작자에게 연결하는 절, 도구
불특정 언어(제품명이 아니라 "브라우저 접근" 같은 능력 단위), 내장 강제 장치(아래
Pre-Flight 원칙 참조). 모호하면 오픈소스를 기본값으로 하고 구체 정보를 제거해 일반화한다.

**내부(internal) 스킬**: 사용자/클라이언트/프로젝트 특정 정보나 개인 선호를 담는다.
스스로 internal임을 명시하며 저작자 표시나 라이선스가 필요 없다. 작업 문서이므로 최신
상태만 유지하면 되고 과도한 설계가 불필요하다.

**이 프로젝트에서의 적용**: otask_observer 자체는 오픈소스 이식본(원본 크레딧 보존)이며,
이 스킬을 통해 신규 생성되는 각 관찰 항목의 `Type` 필드(open-source | internal)는 위
분류를 그대로 사용한다. 프로젝트 고유 정보(경로, 세션 UUID, 특정 스킬명)가 포함된 관찰은
`internal`로 표기한다.

## Pre-Flight 원칙 (사전 비행 점검)

스킬에 문서화된 규칙은 창작 흐름 중 신뢰성 있게 지켜지지 않는다. 명시적 규칙이 있는
모든 스킬은 산출물을 규칙과 대조 검증하는 단계가 필요하다. 스킬을 만들거나 개선할 때
항상 묻는다 — "규칙이 있는가? 그 규칙을 강제하는 장치가 있는가?" 없다면 추가한다.

**내장된 명령어도 사전 점검 대상이다** — 산문 규칙과 명령 스니펫은 실패 양상이 다르다.
산문 규칙은 실행마다 맥락에서 재해석되므로 모호함이 실행 시점에 걸러지지만, 내장된
명령은 그대로 무기한 실행되며 미묘하게 틀린 명령이 매번 재검토를 통과할 수 있다
(`git log -1 --format=%cI --reverse`는 `-1`이 `--reverse`보다 먼저 적용되어 최신 커밋을
반환하는데, 직관적으로는 "가장 오래된 커밋"으로 읽힌다). 스킬 파일에 내장된 명령은
저장 전 실제 데이터로 1회 실행하고 결과의 타당성을 확인해야 한다. 검증 안 된 스니펫은
스킬에서 가장 위험한 줄에 속한다 — 어떤 재검토로도 못 잡는 버그를 실어 나른다.

이 프로젝트의 CLAUDE.md "재발방지 = 물리적 강제" 원칙과 동일 사상이다. otask_observer의
번호 부여 규율(사전확인→쓰기직전재확인→쓰기후검증)이 이 원칙의 구체 적용 사례다.

## 린 콘텐츠(Lean Content)

스킬은 실행 시점의 에이전트 행동을 바꾸는 내용만 담아야 한다. 변경 이력, 저작자 표시
이외의 크레딧, 긴 배경 설명, 유지보수 메모는 보조 문서로 옮긴다. 예시·안티패턴·실전
시나리오는 자르지 않는다 — 맥락 없는 규칙은 맥락 있는 규칙보다 더 자주 위반된다. 판별
기준 — "이걸 지우면 행동이 바뀌는가?" 세션마다 로드되는 스킬 본문 규칙과, 필요할 때만
로드하는 참조 파일의 일화적 내용(progressive disclosure)을 구분한다.

## 라이선싱

전문(preamble)에 라이선스 문구를, 필요 시 LICENSE 파일에 전문을 포함한다. 선택지 —
**CC BY 4.0**(산문/방법론 스킬 권장 기본값), **MIT**(코드 중심, 허용적), **Apache 2.0**
(MIT + 특허 보증), **CC BY-SA 4.0**(파생물 동일 조건 공유), **GPL 계열**(강한 카피레프트).
otask_observer는 원본이 CC BY 4.0이므로 이식본도 동일 라이선스를 유지한다 — 이식이
파생물에 해당하므로 원저작자 표시를 계속 보존해야 한다(법적 의무).

## 저작자 표시 템플릿 (원본)

```markdown
**Created by [저작자명] / [웹사이트 또는 연락처]**

[스킬이 하는 일과 출처에 대한 1~2문장 설명]

**Licence:** 이 스킬은 [라이선스명] 하에 배포된다. [1문장 요약]

**Feedback & Support:** 방법론에 관한 의문이나 건설적 피드백이 있으면 공개 저장소에
이슈를 남기도록 권장한다 — 공개 피드백은 모든 사용자에게 이롭다. 직접 연락: [연락처].
피드백이 방법론에서 비롯된 것이면 기록하고 공유를 제안하고, 에이전트가 스킬 규칙을 안
지킨 것이 원인이면 인정하고 바로잡는다.
```

이 이식본(otask_observer/SKILL.md)은 위 템플릿의 정신을 반영해 상단에 원저작자·라이선스·
원본 URL 블록을 배치했다.

## 기밀성 계층 (5단계)

오픈소스/internal 경계는 곧 기밀성 경계이며, 어느 한 계층이 놓쳐도 다른 계층이 잡도록
겹겹이 방어한다.

1. **관찰 단위 정제** — 오픈소스 관찰의 Principle 필드는 완전히 일반화한다.
2. **작성 전 리뷰** — 오픈소스 스킬 초안 작성/재생성 전, 소스 자료 전체에서 클라이언트명·
   URL·도메인·내부 용어·식별 가능한 특정 구조를 스캔해 일반 표현으로 먼저 치환한다.
3. **작성 후 스윕** — 누출만 집중적으로 재검토한다. 저작자 외 고유명사, 도메인/URL/
   프로젝트 식별자, 클라이언트를 좁힐 수 있는 세부 정보, 실제 프로젝트로 추적 가능한
   예시.
4. **구조적 원칙** — 애매하면 제거한다. 약간 더 일반적인 편이 약간 더 새는 것보다 낫다.
5. **교차 재식별 최종 스윕** — 공개 전 마지막 패스. 개별적으로는 안전한 예시들이 조합되면
   특정 클라이언트를 식별시킬 수 있다(공개된 클라이언트 목록과 일치하는 개수, 좁은
   업종의 구체적 숫자, 같은 업종의 살짝 위장된 가짜 이름). 모든 예시와 그 필드(업종,
   지역, 숫자, 시점, 개수)를 목록화하고, 저작자의 공개 클라이언트 목록을 아는 독자가
   매칭할 수 있는지 자문한다. 개수를 흐리거나, 업종을 넓히거나, 예시 범위로 바꾸거나,
   합성 사례로 통합해 완화한다. 이 패스는 기계적으로 수행한다 — 저작자 본인은 진실을
   알기 때문에 가장 신뢰할 수 없는 판정자다.

이 프로젝트에서는 관찰 로그 자체가 `session-env/${UUID}/` 하위(세션 스코프, 비공개)에
있으므로 즉각적인 공개 위험은 낮으나, 승격되어 LESSONS.md(영구, 저장소 커밋 대상)로
올라가는 순간부터는 위 5계층 정제를 거쳐야 한다 — 특히 사용자 개인정보·프로젝트 경로 등이
LESSONS.md에 그대로 노출되지 않도록 odone_lesson 승격 단계에서 검토한다.

## 스킬 편집 — 항상 라이브 파일에서 시작

1. 라이브 파일이 유일한 권위 소스다. 이 프로젝트에서는 `.claude/skills/{skill}/SKILL.md`.
2. 항상 라이브 파일을 새로 읽은 뒤 편집한다 — 작업 사본, 이전 초안, 기억을 기준으로
   삼지 않는다.
3. 스테이징/작업 사본을 덮어쓰기 전에 라이브 파일과 diff한다. 다르면 라이브 버전 기준으로
   재작업한다.
4. 원본은 "스테이징 전용, 사용자 설치 전까지 라이브 미반영"을 안전장치로 삼지만, 이
   프로젝트는 odev/odone 파이프라인이 이미 검증·리뷰 단계를 갖추고 있으므로 직접 라이브
   파일을 수정하는 기존 방식(Surgical Changes 원칙 하 담당 파일만 수정)을 그대로
   따른다 — 별도 스테이징 디렉토리를 신설하지 않는다. 이는 원본과의 의도적 차이점이다.

## 재구성 검증 (내용 이동 시)

콘텐츠를 축약 없이 이동(핵심+참조로 분리, 병합, 재구조화)할 때 "아무것도 유실되지
않았다"는 기계적으로 검증 가능하다.

1. 원본과 신규 베이스의 `diff`로 추가/이동된 모든 줄을 열거한다.
2. 재구성된 파일 세트 전체에서 각 비어있지 않은 줄을 정확 매칭(`grep -F`)한다.
3. 누락으로 보이는 항목은 결론 내리기 전에 특징적인 중간 부분 문자열로 실질 검토한다 —
   대부분의 누락은 컨테이너 변경(제목 레벨 변화, 목록↔산문 전환, 줄바꿈 재배치)이지
   실제 유실이 아니다.
4. 파일별 단어 수 정합성 점검.

한 계층만으로는 실질 검토만 하면 유실을 놓치고, 정확 매칭만 하면 오탐이 많다. 추가로
원본의 강제 메커니즘(체크포인트, 단언, 불변식, 필수 쓰기 규칙, 기본값)을 명시적
체크리스트로 인벤토리하고 — 압축은 강제 장치를 중복으로 오인해 우선 제거하는 경향이
있다 — "순수 재구성"이라 주장하는 변경에 새로운 동작이 숨어 있지 않은지 스윕한다.

## 신규 스킬

신규 스킬 생성은 `skill-creator` 스킬을 활용한다(가용 시). 유형을 먼저 정한다 — 오픈소스면
정제·일반화, internal이면 구체 정보 자유 포함, 불확실하면 오픈소스를 기본값으로 하고
사용자가 나중에 internal 세부사항을 추가하게 한다.

## 원칙 전파(Principle Propagation)

관찰의 Principle이 스킬 전반에 적용된다면 `Skill: All skills`로 기록하고 노출한다.
사용자가 승인하면 교차 원칙 문서(이 프로젝트에서는 CLAUDE.md의 관련 섹션 또는
LESSONS.md 상단)에 추가한다. 전파 시점은 즉시(모든 스킬 지금 갱신 — 기밀성 규칙 같은
경우) 또는 기회적(각 스킬의 다음 갱신 시 적용) 중 선택한다.
