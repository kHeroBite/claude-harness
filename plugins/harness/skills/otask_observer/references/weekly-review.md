# 종합 검토 절차 (odone_lesson 연동 참조본)

이 파일은 원본 Task Observer의 "Comprehensive Review" 절차를 한국어로 이식한 참조본이다.
이 프로젝트에서 실제 검토 실행 주체는 **odone_lesson 파이프라인**(odone_trans →
odone_review → odone_hooks/odone_skills/odone_docs)이며, 본 파일은 그 절차가 참고할 수
있는 상세 로직을 담는다. otask_observer 자체는 독립된 예약 실행 주체를 갖지 않는다 —
원본의 "예약 자동 실행(Scheduled autonomous review)" 개념은 이 환경에 없다 (팀에이전트
하네스에 크론/예약 스케줄러가 결합되어 있지 않음). 대신 odone 단계 진입 시점이 곧
검토 시점이다.

## 실행 시점

원본은 두 모드(예약 자동 실행 / 세션 시작 시 7일 폴백)를 정의하나, 이 환경에서는 다음
1가지로 단순화한다.

- **odone_lesson 진입 시점 검토**: odone_lesson의 Step ①(odone_trans)~②(odone_review)
  실행 중, 현재 세션의 `logs/observations.md`에 존재하는 OPEN 항목 전체를 자동 스캔한다.
  파이프라인이 도는 매 사이클마다 발생하므로 원본의 "7일 폴백"보다 촘촘하다.
- 사용자에게 "검토를 지금 실행할지" 묻는 인터랙티브 오퍼는 생략한다 — odone 단계는 이미
  자동 파이프라인의 일부이므로 별도 승인 절차 없이 진행한다 (이 프로젝트의 ofinish
  autoloop 강제 정책과 동일한 사상).

## 작업 큐 구성 (구조적 식별자 기준 — 원본 규칙 그대로 이식)

OPEN 집합의 정의는 "Status가 문자 그대로 OPEN이거나, Status 줄 자체가 없는 항목"이다.

1. `### Observation OBS-N:` 헤더를 전수 열거한다 — 이것이 로그의 권위 있는 항목 목록이다.
2. 각 헤더에 대해 본문 내 `**Status:**` 줄의 유무와 값을 확인한다. 없음/공백/ACTIONED도
   DECLINED도 아닌 값은 전부 OPEN으로 취급한다.
3. `grep '**Status:** OPEN'` 단독 결과만으로 큐를 만들지 않는다 — 선택적 필드에 대한
   grep은 그 필드가 없는 항목을 조용히 누락시킨다. 헤더 목록에서 확정 처리된
   (ACTIONED/DECLINED) 항목을 뺀 나머지로 큐를 구성한다.

**정합성 가드**: `헤더 개수 == 상태분류된 항목 개수`를 항상 확인한다. 차이가 있으면 그
차이는 Status 필드 누락 항목이며, 로그가 깨끗하다고 넘어가지 말고 OPEN으로 간주해
검토 대상에 포함한다.

## 승격 판정 절차 (OBS → L- — SKILL.md "odone_lesson 연동" 절의 상세)

1. OPEN 항목마다 그 원칙(Principle)이 다른 스킬에도 일반화되는지 함께 점검한다 —
   Observation 헤더에 적힌 스킬명 하나로 국한하지 않는다.
2. `odone_review`의 Level 1/2/3 분류를 그대로 적용한다.
   - Level 1(1회성) → LESSONS.md에 참고용으로만 남기거나 승격 보류.
   - Level 2(반복 가능성) → 대상 스킬 SKILL.md 규칙 보강 + LESSONS.md L-NNN 신규 기록.
   - Level 3(2회+ 반복 확인) → hook 물리 차단 또는 oio 서버 수정 + LESSONS.md L-NNN 기록.
3. 승격된 항목은 원본 OBS 항목에 `ACTIONED (YYYY-MM-DD) — L-NNN으로 승격`을 기록한다.
   날짜는 필수다 — 날짜가 없으면 아카이브 대상 판정이 깨진다.
4. 승격되지 않은 항목은 `DECLINED (YYYY-MM-DD) — 사유`로 명시한다.
5. SIMPLIFY 신호가 붙은 항목은 별도로 모아 "삭제/단순화 후보" 목록으로 odone_review
   출력에 포함시킨다 — 이 프로젝트 LESSONS.md에 없던 축이므로 시작 단계에서는 자동
   삭제하지 않고 사람이 판단할 후보로만 제시한다.

## 반영 시 규칙

- 승격 시 대상 스킬의 SKILL.md를 갱신할 때는 관찰 목록을 파일 하단에 그냥 붙이지 않는다
  — 통찰이 논리적으로 속하는 섹션에 통합한다. 구조·어조·기존 크레딧 블록을 보존한다.
- 하나의 관찰만으로 광범위한 재구성을 하지 않는다. 추가적이고 명백히 안전한 변경(새 규칙
  1줄, 명확화, 사실 오류 수정)은 바로 반영 가능하나, 구조 변경/신규 능력/방법론 변경은
  더 신중한 검토(예: 사용자 확인 또는 advisor 자문)를 거친다.
- 신규 스킬 후보는 이 검토 절차에서 바로 생성하지 않는다 — 후보로 명시하고 사용자/
  team-lead 판단에 맡긴다.

## 아카이브 (선택 사항)

원본은 해결된 항목을 날짜별 아카이브 파일로 옮기는 절차를 정의한다. 이 환경에서는
관찰 로그가 세션 스코프(`session-env/${UUID}/logs/observations.md`)이므로 세션이
끝나면 파일 자체가 정리 대상이 될 수 있다 — 따라서 별도 아카이브 디렉토리를 강제하지
않는다. 다만 같은 세션이 장시간 지속되며 로그가 길어지는 경우, 병렬 로그 안전 5원칙을
지키며 이미 확정 처리(ACTIONED/DECLINED)되고 날짜가 오늘 이전인 항목만 라이브 로그
하단의 "## 아카이브" 섹션으로 이동해도 무방하다. 오늘 처리된 항목은 유예 기간을 두고
남겨둔다 — 유예는 파일에 기록된 날짜로 판단하며 세션 기억으로 판단하지 않는다.

## 제약 사항 (원본 그대로 이식)

- 관찰 항목의 Status 필드 이외의 내용은 검토 과정에서 임의로 수정하지 않는다.
- 검토 중 신규 스킬을 만들지 않는다 — 후보만 기록한다.
- 반영 방법이 불확실하면 건너뛰고 그 사실을 요약에 남긴다.
- internal 관찰도 open-source 관찰과 동일한 엄격도로 다룬다.
